# Watchly architecture

The React application uses same-origin Worker APIs and native WebSockets. Each seven-character room code maps to one SQLite Durable Object. Supabase retains accounts/social records, LiveKit carries camera/microphone tracks, and screen sharing remains authorized P2P with three viewers. Local movie bytes stay on the devices; room messages contain metadata and controls. Drive is authorized per selected file and streams Range responses, optionally through the signed existing Render bridge.

`backend/realtime.js` is the shared transport-independent room engine. `backend/roomAccess.js` owns admission, password records, approval, invitation expiry/revocation and unbanning. `shared/playback-core.mjs` owns canonical time, rate, transitions and drift decisions used by the server and browser. Playback adapters expose actual native/embed capabilities; source resolution, local-file ownership, subtitle/remux code, clock sampling, recovery and queue convergence live in separate modules. Existing YouTube playlist readiness/discovery and wire compatibility remain.

Storage schema **3** separates metadata, video/canonical playback, membership, queue/chat records, sets/bans, commands, minimal connections, compact ACKs, access policy, hashed invitations, approvals, presence outbox, media jobs and webhook receipts. Schema 1 migrates atomically; schema 2 upgrades without rewriting domain records. Old schema-2 Workers reject version 3, preventing rollback from silently dropping private-room controls. SQL failure quarantines mutated memory and aborts/reconstructs instead of serving rolled-back state. Dirty-table plans avoid serializing unrelated collections for ordinary mutations. Read-only/rejected/ephemeral events do not rewrite room records.

Auth, password KDF, friend invitation RPC, provider room creation, presence and participant removal perform network/expensive work outside the room mutation queue. Completion rechecks live membership, policy revision and ownership. Per-socket ordering and bounded admission remain. Presence updates are a durable versioned outbox; the indexed directory has leases, idempotent source versions, targeted notifications and bounded retry/terminal retention. It remains one directory: a 500-account simulation is evidence, not a claim of 10,000-account production capacity.

Native clients negotiate queue deltas and delivery receipts. The server bounds pending delivery to 128 KiB/32 frames, caps logical frames at 4 MiB and object queues at 16 MiB, chunks large snapshots, and checks bufferedAmount where exposed. Incomplete transfers expire and reconnect for a snapshot. Receipts track application delivery, not browser rendering or an absolute network-buffer guarantee. Older clients retain existing framing and platform buffer checks.

Daily application counters separately gate new rooms, social lookups and new call tokens. Defaults are 1,000/10,000/100 per UTC day; these count admissions, not billed provider resources. Active playback is not routed through that counter. Diagnostics aggregate 256 events in memory without identities, tokens or persistent telemetry.

The legacy Socket.IO service remains available for rollback/Drive fallback. Its rooms do not share authority with native rooms. Production cutover requires draining/rejoining, compatible storage and explicit authorization. No service was retired or deployment performed.
